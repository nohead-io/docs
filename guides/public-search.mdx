Public search finds published records straight in the search engine, with a **search token** instead of an API key: results come back as fast as you type, and the searches don't count toward your API requests. Use it from your site's browser code or from your own backend. Search runs on [Meilisearch](https://www.meilisearch.com), so its clients and [InstantSearch](https://www.algolia.com/doc/guides/building-search-ui/what-is-instantsearch/js/) work as they are.

Your servers can also search with an API key, through [the API](/guides/api-search): that returns full records, with `expand`.

You need three things: the search URL, a token, and the index name of each collection you search.

## Include collections in public search

Tokens find only collections included in public search. In the web app, open a collection's **Search** tab and turn on **Public search**, or turn it on when you create the collection. It is off by default, and it applies to every token of the project, so a collection you include later is searchable with the tokens you already have. Through the API, it is the collection's `public_search`.

A token finds only the **published** records of included collections. The search engine enforces that: other collections, other projects and unpublished records stay out of reach, whatever a request asks for. Including or removing a collection reaches every token within seconds.

<Warning>
A token is public: in a site, it goes in your page source. Every field of the published records it finds can be read with it, so keep private content out of public search. That includes the fields a [relation field picks](#images-and-related-records) from another collection: they come along whether or not that collection is in public search.
</Warning>

## Index names

Each collection has its own index. Its name shows on the collection's **Search** tab, under **Public search index name**, while the collection is included in public search. Through the API, it is the `index` of the collection's search index:

```bash
# An API key with schema:read
curl "https://api.nohead.io/v1/collections/blog-posts/search-index" \
  -H "Authorization: Bearer $NOHEAD_API_KEY"
```

Index names are opaque and never change, so you can keep them in your code or configuration.

## Create a token

In the web app, open your project's **Search tokens** page, choose **New search token** and name it after the site or app that will use it. Copy the token from the list. Make one per site or app, so deleting one stops only that site's searches. A project can have 25 tokens.

## Search

Send searches to `https://search.nohead.io`, the search URL for every token (a token's `search_url` in the API). It lets searches through and nothing else, and limits how many requests one address can make:

```javascript
const response = await fetch("https://search.nohead.io/multi-search", {
  method: "POST",
  headers: {
    Authorization: `Bearer ${token}`,
    "Content-Type": "application/json",
  },
  body: JSON.stringify({
    queries: [{ indexUid: index, q: "lentil", limit: 10 }],
  }),
})
const { results } = await response.json()
for (const hit of results[0].hits) console.log(hit.data.title)
```

Hits look like records:

- `id` (`rec_…`), and `published_at`, `created_at` and `updated_at` as Unix seconds; `published_at` can be filtered and sorted on, such as `filter: "published_at > 1767225600"` for posts published since 2026
- field values under `data`, by field key: dates as Unix seconds, rich text as plain text, JSON as a string, assets and relations as IDs
- `expanded`: what asset and relation fields return of the assets and related records they point at ([below](#images-and-related-records))

Hits hold the fields their collection includes, which is all of them unless you leave some out ([Included](/guides/content-modelling#search-options)).

Several collections at once take one query each, or a federated search across them (`federation: {}` in the request).

## Images and related records

An asset or relation field holds IDs in `data`, and under `expanded` what its `expanded` setting lists, so a result can show its image and its author with no other request:

- An **asset field** expands an image's `image_url`, `width` and `height` (**Dimensions**) and `alt` text, and any file's `file_url`, `filename` and `content_type`. By default it expands an image's URL and dimensions where the field takes images, and a file's URL and filename where it takes other files, both while it takes any file. `image_url` and the dimensions are `null` for a file that isn't an image; build resized versions from `image_url` as in [Images](/guides/images), and link `file_url` to download the file.
- A **relation field** expands nothing by default: `data` holds the related records' IDs. Pick fields of the related collection, such as an author's name and portrait, and each published related record comes along with them, by their keys. The related collection doesn't need to be in public search.

Pick them in the web app, on a collection's **Search** tab: the gear beside an asset or relation field opens its **Search options**, where **Included in public search results** lists its asset parts or related fields. With the API or a [schema file](/guides/schema-as-code), it's the field's `expanded` setting: a relation lists the related collection's fields by ID (`fld_…`) in the API, and by key in a schema file.

`expanded` shapes public search hits only. API reads embed whole related records and assets with `?expand=`, at request time ([Reading content](/guides/reading-content)).

```javascript
// With Cover (URL and dimensions) and Authors (name) included:
const hit = results[0].hits[0]
hit.expanded.cover // { id: "ast_…", image_url: "https://images.nohead.io/plain/…", width: 2000, height: 1333 }
hit.expanded.authors // [{ id: "rec_…", data: { name: "Leela Menon" } }]
```

A single value is the asset or record, or `null` once it's gone; a list holds those that still exist (at most 100 related records). When an expanded value changes, such as an author renamed or unpublished, the hits that expand it follow.

What searches match of related records is chosen apart from what hits return: a searchable relation field matches the related text fields its `searched` setting lists (**Searchable** in the web app lists them), whether or not hits return them, so "Menon" finds Leela Menon's posts. A job search can match company names while its hits return each company's name and logo. A filterable relation field also filters and counts on the related fields of both lists, under `data` when hits return them and under `searched` when they don't: `filter: 'expanded.authors.data.name = "Leela Menon"'`, `facets: ["expanded.category.data.name"]` for a filter list by category name, or `facets: ["expanded.authors.searched.role"]` for a role hits don't show. A related field's path follows its list, so moving it between what searches match and what hits return moves its filters too. Names can repeat, so filter by ID (`data.category = "rec_…"`) to be exact.

## Filter and sort

Fields take part in searches by their [search settings](/guides/content-modelling#search-options), as in every search: words match `searchable` fields, and `filterable` and `sortable` fields can be used in filters and sorts, whether or not hits include them. Name them under `data`:

```javascript
{ indexUid: index, q: "soup", filter: 'data.cuisine = "french"', sort: ["published_at:desc"] }
```

Dates are Unix seconds here too: `'data.starts_on >= 1790812800'` finds records from 1 October 2026 (00:00 UTC) on.

## Highlight

To mark the words that matched, name fields by their path in `attributesToHighlight`, and shorten long text around them with `attributesToCrop`. The marked-up copy of the hit is its `_formatted`:

```javascript
{
  indexUid: index,
  q: "lentil",
  attributesToHighlight: ["data.title"],
  attributesToCrop: ["data.summary"],
  cropLength: 20,
}
// hit._formatted.data.title: "<em>Lentil</em> soup"
```

A related record's fields highlight as its whole `data`: `expanded.authors.data` marks the authors' names in `_formatted.expanded.authors`, while a path inside it, such as `expanded.authors.data.name`, marks nothing. `["*"]` highlights every field. The highlighted text comes from your content, so escape it before inserting it as HTML and turn only the `<em>` tags back into markup, or set your own tags with `highlightPreTag` and `highlightPostTag`.

## Facets

Facets count the hits per value of a `filterable` field, for filter lists such as "French (12)". Ask for them with `facets`:

```javascript
{ indexUid: index, q: "soup", facets: ["data.cuisine", "data.servings"] }
```

Each result then has a `facetDistribution`, counted over the hits that match the query and filters, and a `facetStats` with the lowest and highest value of number and date fields, for range sliders:

```json
{
  "facetDistribution": { "data.cuisine": { "french": 12, "italian": 8 }, "data.servings": { "2": 9, "4": 11 } },
  "facetStats": { "data.servings": { "min": 2, "max": 4 } }
}
```

- **Fields that facet well** have a few values shared by many records: enums, booleans, and short text such as a brand or a city. Fields with several values count each value once per record, so tags work as facets.
- **Relations and assets count by ID** (`rec_…`, `ast_…`). To show names, look them up, or keep an enum or text field next to the relation.
- **Up to 100 values** are returned per facet, and only for published records, like hits.
- **In a federated search**, name the facets per index in the federation instead, `federation: { facetsByIndex: { [index]: ["data.cuisine"] } }`, and read them from the response's `facetsByIndex`. A query's own `facets` is refused there.

To find values within a facet as someone types (InstantSearch's `refinementList` with `searchable: true`), search them:

```javascript
const response = await fetch(`https://search.nohead.io/indexes/${index}/facet-search`, {
  method: "POST",
  headers: { Authorization: `Bearer ${token}`, "Content-Type": "application/json" },
  body: JSON.stringify({ facetName: "data.cuisine", facetQuery: "ita" }),
})
const { facetHits } = await response.json() // [{ value: "italian", count: 8 }]
```

## InstantSearch

```javascript
import instantsearch from "instantsearch.js"
import { searchBox, hits } from "instantsearch.js/es/widgets"
import { instantMeiliSearch } from "@meilisearch/instant-meilisearch"

const { searchClient } = instantMeiliSearch("https://search.nohead.io", token)

instantsearch({ indexName: index, searchClient })
  .addWidgets([
    searchBox({ container: "#search" }),
    hits({ container: "#hits", templates: { item: (hit, { html }) => html`${hit.data.title}` } }),
  ])
  .start()
```

## Rename or delete a token

Rename a token or delete it from its menu on the **Search tokens** page. A renamed token stays the same. A deleted one fails at once, and your other tokens keep working. To stop searches of one collection, remove it from public search instead. While a project or organization is scheduled for deletion its tokens stop working, and they work again if it is restored.
