Public search finds published records straight in the search engine, with a **search token** instead of an API key: results come back as fast as you type, and the searches don't count toward your API requests. Use it from your site's browser code or from your own backend. Search runs on [Meilisearch](https://www.meilisearch.com), so its clients and [InstantSearch](https://www.algolia.com/doc/guides/building-search-ui/what-is-instantsearch/js/) work as they are.

Your servers can also search with an API key, through [the API](/guides/api-search): that returns full records, with `expand`.

You need three things: the search URL, a token, and the index name of each collection you search.

## Include collections in public search

Tokens find only collections included in public search. In the web app, open a collection's **Search** tab and turn on **Include in public search**, or turn it on when you create the collection. It is off by default, and it applies to every token of the project, so a collection you include later is searchable with the tokens you already have. Through the API, it is the collection's `public_search`.

A token finds only the **published** records of included collections. The search engine enforces that: other collections, other projects and unpublished records stay out of reach, whatever a request asks for. Including or removing a collection reaches every token within seconds.

<Warning>
A token is public: in a site, it goes in your page source. Every field of the published records it finds can be read with it, so keep private content out of public search.
</Warning>

## Index names

Each collection has its own index. Its name shows on the collection's **Search** tab, under **Public search index name**, while the collection is included in public search. Through the API, it is the `index` of the collection's search index:

```bash
# An API key with schema:read
curl "https://api.nohead.io/v1/collections/blog-posts/search-index" \
  -H "Authorization: Bearer $NOHEAD_API_KEY"
```

Index names are opaque and never change, so you can keep them in your code or configuration.

## Create a token

In the web app, open your project's **Search tokens** page, choose **New search token** and name it after the site or app that will use it. Copy the token from the list. Make one per site or app, so deleting one stops only that site's searches. A project can have 25 tokens.

## Search

Send searches to `https://search.nohead.io`, the search URL for every token (a token's `search_url` in the API). It lets searches through and nothing else, and limits how many requests one address can make:

```javascript
const response = await fetch("https://search.nohead.io/multi-search", {
  method: "POST",
  headers: {
    Authorization: `Bearer ${token}`,
    "Content-Type": "application/json",
  },
  body: JSON.stringify({
    queries: [{ indexUid: index, q: "lentil", limit: 10 }],
  }),
})
const { results } = await response.json()
for (const hit of results[0].hits) console.log(hit.data.title)
```

Hits look like records:

- `id` (`rec_…`), and `published_at`, `created_at` and `updated_at` as Unix seconds; `published_at` can be filtered and sorted on, such as `filter: "published_at > 1767225600"` for posts published since 2026
- field values under `data`, by field key: dates as Unix seconds, rich text as plain text, JSON as a string, and assets and related records as objects with what showing them takes (below)

Several collections at once take one query each, or a federated search across them (`federation: {}` in the request).

## Images and related records

A hit carries what a result shows, so a site needs no lookups. Where records keep IDs in `data`, hits hold objects with the ID inside:

```json
{
  "id": "rec_…",
  "data": {
    "title": "Lentil soup",
    "cover": { "id": "ast_…", "image_url": "https://images.nohead.io/plain/…", "alt": "A bowl of soup", "width": 1600, "height": 1067 },
    "authors": [{ "id": "rec_…", "data": { "name": "Leela Rao" } }],
    "category": { "id": "rec_…", "data": { "name": "Studio", "slug": "studio" } }
  }
}
```

- **An asset** has its `image_url`, the whole image: resize it for your results with [image options](/guides/images), such as `imageUrl(hit.data.cover, { width: 144, height: 108, fit: "cover" })` with the TypeScript SDK. `image_url` is null for files that aren't images and for deleted assets, so check it before building a URL.
- **A related record** is a partial record: its `id`, and in `data` its title field (its collection's first text field holding a single value) and slug field, by their keys. Link to it by its slug.
- **Only public, published content shows.** A related record shows while it is published and its own collection has public search on too. Otherwise it keeps its `id`, with `data: null`; an asset that's deleted keeps its `id` with the rest null.
- **Related names match** the search words, so "Leela" finds her posts. Turn `searchable` off on the relation field if they shouldn't. An asset field you make `searchable` matches its alt text.
- **They stay current:** renaming, publishing or unpublishing a related record updates the hits that show it within seconds, and so does turning off its collection's public search. Changing which fields a related collection shows, or turning its public search on, rebuilds the indexes that relate to it.

## Filter and sort

Fields take part in searches by their [search settings](/guides/content-modelling#search-options), as in every search: words match `searchable` fields, and `filterable` and `sortable` fields can be used in filters and sorts. Name them under `data`:

```javascript
{ indexUid: index, q: "soup", filter: 'data.cuisine = "french"', sort: ["published_at:desc"] }
```

Dates are Unix seconds here too: `'data.starts_on >= 1790812800'` finds records from 1 October 2026 (00:00 UTC) on.

A `filterable` relation filters by the related record's ID, or by its title or slug, which suits filters in a page's URL:

```javascript
{ indexUid: index, filter: 'data.category.data.slug = "studio"' } // or 'data.category.id = "rec_…"'
```

## Highlight

To mark the words that matched, name fields by their path in `attributesToHighlight`, and shorten long text around them with `attributesToCrop`. The marked-up copy of the hit is its `_formatted`:

```javascript
{
  indexUid: index,
  q: "lentil",
  attributesToHighlight: ["data.title"],
  attributesToCrop: ["data.summary"],
  cropLength: 20,
}
// hit._formatted.data.title: "<em>Lentil</em> soup"
```

`["*"]` highlights every field. The highlighted text comes from your content, so escape it before inserting it as HTML and turn only the `<em>` tags back into markup, or set your own tags with `highlightPreTag` and `highlightPostTag`.

## Facets

Facets count the hits per value of a `filterable` field, for filter lists such as "French (12)". Ask for them with `facets`:

```javascript
{ indexUid: index, q: "soup", facets: ["data.cuisine", "data.servings"] }
```

Each result then has a `facetDistribution`, counted over the hits that match the query and filters, and a `facetStats` with the lowest and highest value of number and date fields, for range sliders:

```json
{
  "facetDistribution": { "data.cuisine": { "french": 12, "italian": 8 }, "data.servings": { "2": 9, "4": 11 } },
  "facetStats": { "data.servings": { "min": 2, "max": 4 } }
}
```

- **Fields that facet well** have a few values shared by many records: enums, booleans, and short text such as a brand or a city. Fields with several values count each value once per record, so tags work as facets.
- **Relations count by ID, title or slug:** `facets: ["data.category.data.slug"]` gives `{ "studio": 12, "kitchen": 8 }`, slugs ready for links. Facet by the title field (`data.category.data.name`) for labels. Assets count by ID only.
- **Up to 100 values** are returned per facet, and only for published records, like hits.
- **In a federated search**, name the facets per index in the federation instead, `federation: { facetsByIndex: { [index]: ["data.cuisine"] } }`, and read them from the response's `facetsByIndex`. A query's own `facets` is refused there.

To find values within a facet as someone types (InstantSearch's `refinementList` with `searchable: true`), search them:

```javascript
const response = await fetch(`https://search.nohead.io/indexes/${index}/facet-search`, {
  method: "POST",
  headers: { Authorization: `Bearer ${token}`, "Content-Type": "application/json" },
  body: JSON.stringify({ facetName: "data.cuisine", facetQuery: "ita" }),
})
const { facetHits } = await response.json() // [{ value: "italian", count: 8 }]
```

## InstantSearch

```javascript
import instantsearch from "instantsearch.js"
import { searchBox, hits } from "instantsearch.js/es/widgets"
import { instantMeiliSearch } from "@meilisearch/instant-meilisearch"

const { searchClient } = instantMeiliSearch("https://search.nohead.io", token)

instantsearch({ indexName: index, searchClient })
  .addWidgets([
    searchBox({ container: "#search" }),
    hits({ container: "#hits", templates: { item: (hit, { html }) => html`${hit.data.title}` } }),
  ])
  .start()
```

## Rename or delete a token

Rename a token or delete it from its menu on the **Search tokens** page. A renamed token stays the same. A deleted one fails at once, and your other tokens keep working. To stop searches of one collection, remove it from public search instead. While a project or organization is scheduled for deletion its tokens stop working, and they work again if it is restored.
