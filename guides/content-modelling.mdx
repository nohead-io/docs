title: Content modelling

A **collection** is a data model: blog posts, products, team members. It has a name, a **slug** that identifies it in URLs and API calls (`blog-posts`), an optional description and a list of **fields**.

A **field** has:

- a **name** shown to editors ("Cover image");
- an **API key**, the key its value has in a record's `data` (`cover_image`);
- a **type**, such as text, number or relation;
- **required**: whether every record must have a value;
- **multiple**: whether the value is a list (not available for `boolean`, `rich_text` and `json`);
- a type-specific **configuration**, such as a maximum length or enum options.

## Naming rules

| | Rule |
| --- | --- |
| Collection slug | Starts with a letter; lowercase letters, digits, `-` and `_`; at most 63 characters. Unique in the project. |
| Field API key | Starts with a letter; lowercase letters, digits and `_` (snake_case); at most 63 characters. Unique in the collection. |

These field API keys are reserved because records use them for their own attributes: `id`, `object`, `collection`, `data`, `status`, `published_at`, `created_at`, `updated_at`, `deleted_at`, `revision`, `schema_version`.

## Field types

| Type | Value in `data` | Configuration |
| --- | --- | --- |
| `text` | A string, up to 10,000 characters | `min_length`, `max_length`, `format`, `unique` (see [Formats and unique values](#formats-and-unique-values)) |
| `long_text` | A string, up to 100,000 characters | `min_length`, `max_length` |
| `rich_text` | A rich text document: `{"type": "doc", "content": [...]}`, compatible with ProseMirror and Tiptap, which can show [images](#images-in-rich-text) of the project's assets | |
| `integer` | A whole number within ±9,007,199,254,740,991, which every JSON client represents exactly | `min`, `max`, `unique` |
| `decimal` | A number | `min`, `max` |
| `boolean` | `true` or `false` | |
| `date` | A calendar date, `2026-10-09`, returned exactly as written. With `include_time`, a moment: ISO 8601 with an offset, stored in UTC | `include_time`, `time_zone` (see [Dates](#dates)) |
| `enum` | One of the configured options, as a string | `options` (required): up to 500 unique strings |
| `asset` | An asset ID (`ast_...`) from the project's assets | `accepted_types`: the kinds of file it takes |
| `relation` | A record ID (`rec_...`) in the target collection | `target_collection_id` (required) |
| `json` | Any JSON value, up to 1 MB | |

Every type also accepts a `description` (up to 500 characters) shown to editors.

Values are never converted between types: `"5"` is not an integer and `1` is not a boolean. With **multiple** on, the value is a list of distinct values of the field's type, such as a list of tags or photos; a repeated value is refused (`duplicate_value`).

<Note>
  Links and image sources inside rich text must be `http`, `https`, `mailto`, `tel` or relative URLs. Your site renders this content, so the API rejects `javascript:` and `data:` URLs.
</Note>

## Formats and unique values

A `text` field can have a `format`, and values that don't match it are refused with `invalid_format`:

| Format | Takes |
| --- | --- |
| `email` | An email address, kept as entered |
| `url` | An `http` or `https` address. With `relative: true`, also paths within the site, like `/about` |
| `slug` | Lowercase letters, digits and single hyphens, like `hello-world` (no slashes, at most 200 characters) |

`text` and `integer` fields with one value can be `unique`: no two records of the collection have the same value. Emails compare ignoring capitals, records without a value don't count, and a deleted record frees its values. A value another record has is refused with `taken`, and the error names that record's `record_id`. Turning `unique` on is refused while records share a value; fix them first.

A slug for your URLs is a text field with `format: slug` and `unique: true`, and in the editor it is the **Slug** field type. The editor fills a draft's slug from its title as you type (or from the field named in `source_field`) until you edit the slug yourself. Look a record up by slug with `filter[slug]=hello-world`.

## Dates

A plain `date` field holds a day, `YYYY-MM-DD`, with no time and no time zone. It is the same day for everyone, so a publish date or a birthday never shows as the day before. Print it as it is: in JavaScript, `new Date("2026-10-09")` is midnight UTC, which is still 8 October in the Americas.

With `include_time: true` the field holds a moment, such as an event's start. Send it with any offset (`2026-10-09T19:00:00+02:00` or `2026-10-09T17:00:00Z`); it is stored in UTC. Responses write it:

- in UTC (`2026-10-09T17:00:00Z`), by default;
- with the offset of the field's `time_zone` (an IANA name such as `Europe/Copenhagen`), daylight saving included, when the field has one: `2026-10-09T19:00:00+02:00`, and `2026-12-01T19:00:00+01:00` in winter. Your site prints the local time without knowing the zone, and the editor shows and takes times in that zone, whoever is editing.

Changing `time_zone` never rewrites values: the moments stay, and only how they are written changes. Turning `include_time` on or off does rewrite them, so it runs as a [field migration](#changing-a-collection). Removing the time takes a `time_zone` whose day each moment falls on (by default the field's own, else UTC), and adding it makes each date midnight in the field's zone.

## Images in rich text

An image in a rich text document is one of the project's assets, by ID, with its alt text:

```json
{
  "type": "doc",
  "content": [
    {
      "type": "paragraph",
      "content": [{ "type": "text", "text": "The view from the pier." }]
    },
    {
      "type": "image",
      "attrs": {
        "asset_id": "ast_01J9ZQ3F8X5W2K7M4N6P0R1S2T",
        "alt": "A red sky over the sea"
      }
    }
  ]
}
```

- Images go between the document's blocks, not inside a list or a quote.
- A newly added image must be an uploaded JPEG, PNG, GIF, WebP or AVIF of the project; anything else is refused (`invalid_reference`, `type_not_accepted`). SVG files can't be images in rich text, because they can carry scripts. An image already in a document stays when its asset is deleted later.
- A document holds at most 100 images (`too_many_images`). For more, an asset field with **multiple** on suits a gallery better.
- `alt` is up to 1,000 characters, and search matches it.

In the web app, the editor's **Image** button chooses an asset or uploads one, and images can be pasted or dropped in.

To render a document, expand the field: `expanded` then lists the assets its images show, in order, with their dimensions. Then ask for each image's URL at the size your page needs:

```bash
curl "$NOHEAD_API_URL/v1/collections/blog-posts/records?expand=body" \
  -H "Authorization: Bearer $NOHEAD_API_KEY"

curl "$NOHEAD_API_URL/v1/assets/ast_01J9ZQ3F8X5W2K7M4N6P0R1S2T/image-url?width=1200&format=webp" \
  -H "Authorization: Bearer $NOHEAD_API_KEY"
```

A published-only key can read the images that published records show, and nothing of drafts. Alt text is plain text: escape it when you render it, as you would any value.

## Relations and assets

A relation field points at records in another collection of the same project, set by `target_collection_id`. An asset field points at an uploaded file.

An asset field takes any file unless you limit it with `accepted_types`: MIME types or `type/*` wildcards, such as `["image/*", "application/pdf"]`. In the web app, these are the field's **Allowed files** (images, videos, audio, PDFs). The limit applies to newly written values: files already in records are kept, and a new file of another type is refused (`type_not_accepted`). To list only the assets a field takes, pass its types as `content_type` to `GET /v1/assets`.

Records store only the IDs. To get the related records or assets in the same response, pass `expand` with up to five relation, asset or rich text field API keys (for rich text, the assets its images show):

```bash
curl "$NOHEAD_API_URL/v1/collections/blog-posts/records?expand=author,cover_image" \
  -H "Authorization: Bearer $NOHEAD_API_KEY"
```

Each record then has an `expanded` object keyed by field API key. A related record or asset that no longer exists is `null` for a single-value field and left out of the list for a multiple one. With a published-only key, related drafts are left out too.

## Filtering and search

Record lists filter on field values with `filter[<api_key>]=value` (equal), or with an operator, `filter[<api_key>][<operator>]=value`, for `text`, `long_text`, `integer`, `decimal`, `boolean`, `date`, `enum`, `asset` and `relation` fields. Filters combine with AND:

| Operator | Matches | Example |
| --- | --- | --- |
| `eq` (or none) | equal; for a multiple field, lists that contain the value | `filter[category]=shoes` |
| `ne` | not equal, including records with no value | `filter[status][ne]=archived` |
| `gt`, `gte`, `lt`, `lte` | greater or less than, for integer, decimal and date fields with one value | `filter[price][lt]=50` |
| `in` | any of up to 100 comma-separated values (`\,` for a comma inside one) | `filter[category][in]=shoes,bags` |
| `exists` | `true`: has a value, `false`: has none | `filter[cover][exists]=false` |

Values are read as the field's type, so `"5"` is not the integer 5. Dates take `today`, and dates with a time also `now`: `filter[starts_on][gte]=today` lists upcoming events. A plain date's `today` is the day in UTC. A day given for a date with a time covers that day in the field's time zone (UTC without one), so `filter[starts][eq]=2026-10-09` is everything on 9 October there. A date with a time matches the same moment written with any offset. Record lists also filter on `created_at`, `updated_at` and `published_at`, for example `filter[updated_at][gt]=2026-10-01T00:00:00Z` for an incremental sync.

Record lists sort by `created_at` (the default, newest first), `updated_at`, `published_at` or a field: `sort=price`, or `sort=-published_on` for descending. Records with no value come last either way, and text sorts by character code.

Every collection is indexed for full-text search, so members can search any collection in the web app. To let API keys search a collection, turn on search for it (`search_enabled`). The `searchable`, `filterable` and `sortable` options then choose how each field takes part in API searches. Search takes the same filter operators, on `status` and `filterable` fields. Search words match `searchable` fields only, so a field kept out of search can't be probed through it.

## Changing a collection

You can change a collection's name and description at any time. Adding fields, renaming them and changing their options is safe: record data is stored by field ID, so it never moves.

- **Renaming a field's API key** keeps its values. Records come back under the new key, and requests that use the old key keep working for six months, so your code has time to switch.
- **Changing a field's type, making it multiple, or adding or removing a date's time** rewrites stored values, so it runs as a **field migration**. You can preview how many records convert cleanly before you start, and the collection is read-only while the migration runs.
- **Tightening a field** (making it required, lowering a maximum, removing enum options) is refused while existing records would break the new rule. Fix those records first, or run a field migration that fills in a value for them.
- **Deleting a field or collection** is a soft delete, and can be undone.

Each schema change bumps the collection's schema version, and each record carries the `schema_version` it was last written with.
