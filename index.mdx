Nohead stores structured content for your sites and apps. You describe your content as **collections** of typed **fields**, editors write **records** in the web app, and your code reads them over a REST API with an API key.

Every change is a revision, attributed to the person or API key that made it: you can diff and revert record revisions, and schema changes are versioned too. That makes Nohead safe to hand to AI agents: through the CLI or the MCP server, they change content and schema next to your team, and every change they make shows in history and can be undone.

## How it fits together

- **Organizations** hold your team and billing. **Projects** hold content: usually one project per site or app.
- **Collections** are your data models, such as blog posts, products or team members. Each has typed **fields**.
- **Records** are the content itself. They start unpublished and go live when published. Changes to a live record can wait in a **draft** until they are merged into it, now or at a set time.
- **Assets** are the project's uploaded files, such as images and PDFs. Asset fields point at them.
- **[API keys](/guides/api-keys)** belong to a project and carry scopes such as `records:read`. A published-only key never sees unpublished records, which makes it the right key for a live site.

The API reference in the next tab lists every endpoint an API key can call. It is generated from the same OpenAPI document the API is tested against.
